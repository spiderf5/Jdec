# M4 混淆器结构指纹归因

## 可观测形态（字节码 / 容器层面）

厂商归因靠常量池原始 `CONSTANT_Utf8` 字符串里的专属关键词与结构阈值  
（类名集合、方法名长度分布、特定属性 / 注解、加密相关 FQCN）。关键词有强弱  
之分：ProGuard/R8 残留、ZKM 类池专属标记等是专属词；  
`javax/crypto/spec/ivparameterspec` 这类是**通用加密 FQCN**——AES-CBC 也用，  
单独出现不能指向任何特定混淆器。特征是常量池与结构层面的，不含混淆器实现  
代码或反编译片段。  

## 本工具的支持项

对真实 jar 执行 `probe`，基于结构阈值与关键词做厂商归因并给置信度；每项  
指纹有门控，命中必须带证据（命中的关键词 / 阈值）。修复后的归因口径要求：  
**≥ 2 个专属关键词**同时命中才归因到某厂商，且所谓「加密 blob」需另经  
base64 解码与 FQCN 排除复核（见 M5）。输入条件是 jar 可解析、常量池可读；  
产出是带证据的归因结论与混淆度分值。对证据不足者如实报「未命中 / 无法归因」。  

## 已知不覆盖

- 归因词表不等于支持该混淆器的全部机制；命中只说明有厂商结构痕迹，不承诺还原。  
- **旧文档「ZKM 27 enhanced DES」结论是 `probe` 关键词误报**：命中了 AES-CBC  
  也用的 `javax/crypto/spec/ivparameterspec`。经独立金标准核实，  
  `NeoRaven1.1.jar` 常量池里**没有** `DESKeySpec`、`DES/CBC/PKCS5Padding`、  
  `zelix`、`$CodePool` 等 ZKM 专属痕迹。修复后口径下 NeoRaven **不应**被归因为  
  ZKM 27 enhanced DES；本笔记如实记录这一更正，不沿用旧结论。  
- 不处理加密容器内的常量池；不根据单一通用 FQCN 下结论。  
- 不把「未命中专属指纹」写成「已排除 / 已攻克该混淆器」，只写「证据不足，无法归因」。  

## 独立样本与可测点

| 语料 | 可测点 |
| --- | --- |
| `HMCL-3.15.2.exe` | ProGuard / R8 结构痕迹、专属关键词命中数（应 ≥ 2）、混淆度分值 |
| `NeoRaven1.1.jar` | 常量池原始 UTF8 核查：ZKM 专属关键词应为 0、`ivparameterspec` 即使出现也不单独归因 |

## 独立金标准

不取 `probe` 自身输出。用 `zipfile` 取出每个 class 的原始字节，独立解析常量池  
并导出全部 `CONSTANT_Utf8` 字面量，逐一检索专属关键词与通用 FQCN，统计  
「专属关键词命中数」；用 `javap -v` 独立核对。真值问题是「专属关键词命中是否  
≥ 2、`ivparameterspec` 是否只是通用加密词」，不是「probe 打了什么标签」。  

## 负控（构造方式与预期失败）

构造 A：一个 class 的常量池里**只**放 `javax/crypto/spec/ivparameterspec`  
（通用 AES-CBC 也会用），不放任何 ZKM 专属词。预期修复后口径**不得**把它归因  
为 ZKM；若仍归因，则 ≥ 2 专属关键词门控失效。构造 B：放入 ≥ 2 个 ZKM 专属词  
但无加密 blob。预期可归因到厂商，但「enhanced DES 加密」子结论仍须 blob 复核，  
不得仅凭关键词补全。前者直接复现旧误报，用来证明修复生效。  

## 与 03 阶段、独立研究线的边界

03 未在真实语料上做厂商归因的独立金标准核验；本笔记是识别 / 归因级，不是  
解密 / 还原级。ZKM 字符串加密执行引擎还原、BytecodeVM `$CodePool` 复现属  
`ROADMAP:231-236` 独立研究线，永不并入通用恢复承诺，不算 1.0 默认支持项。  
两语料都没有 `$CodePool`、没有 ZKM 专属痕迹，相关目标数为 0，只如实报告，  
不记为已攻克。
