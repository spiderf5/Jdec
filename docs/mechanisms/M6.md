# M6 native 分诊与 PE/JNI 库提取

## 可观测形态（字节码 / 容器层面）

容器层面，MZ stub（`4d5a`）自解压 PE 把 `.dll` / `.so` 作为 overlay 或内嵌  
资源携带；PE 的 COFF / 可选头里有导出表目录，导出名含  
`Java_<pkg>_<Class>_<method>` 形态的 JNI 符号。Java 侧，类的方法访问标志含  
`ACC_NATIVE`，常量池里有对应方法名的 `CONSTANT_Utf8`。特征是文件头、导出表  
与常量池层面的，不含 native 函数体实现代码或反编译片段。  

还有一种是**独立工件布局**：natives 不在主 jar 里，而是由 Maven 的  
`natives-<classifier>` 分类工件单独发布。LWJGL、JNA、Netty 都是这个形态。  
主 jar 声明 native 方法、另一个 jar 才带 `.dll`，所以只扫单一输入必然得到  
「0 个库」——这不是「没有 native」，而是「没找对地方」。  

## 本工具的支持项

对自解压 PE / ELF 与 jar 资源执行 `natives -o` + `analyze -o`：提取 native  
库、解析导出表与 `JNINativeMethod`、报告 Java 侧声明的 native 方法与按名匹配  
的 JNI 符号。`--libs-jar JAR` / `--libs-dir DIR` 用于读取独立工件（可重复给）。  

输入条件是容器可读、PE 头完整、资源条目可枚举；产出是提取出的库文件清单  
（含来源工件）、每库导出数与 `jni=` 数、Java 侧 native 声明数、静态匹配数。  

实测两个互补语料：

| 语料 | 布局 | 结果 |
| --- | --- | --- |
| `HMCL-3.15.2.exe` | 自解压 MZ stub，库在 overlay | 1 库、2 个导出（GPU 请求符号）、69 个 `ACC_NATIVE`、**0 个 JNI 匹配**（导出不是 JNI 符号） |
| LWJGL 2.9.4 | 主 jar + `natives-windows` 分类工件 | 4 库、单库导出 2386、**2674 个 `ACC_NATIVE`**、**2383 个 JNI 符号全部按名命中** |

HMCL 是「有 native 但没有 JNI 导出」的真实反例，LWJGL 是「有 JNI 导出」的  
真实正例，两者一起证明这个计数不是恒真也不是恒假。  

## 已知不覆盖

- 不反编译 native 函数体；不还原寄存器级逻辑。  
- 只做**名字匹配**，不校验签名：`Java_a_B_c` 与声明的 `a/B.c` 同名即算命中，  
  descriptor 不参与比对。  
- 不承诺 `RegisterNatives` 动态绑定还原：运行时注册的 JNI 方法在导出表里没有  
  静态符号，本工具不猜（LWJGL 的 2674 个声明里有 291 个没有静态导出，正是这  
  一类）。  
- 不处理加壳 / 加密的 PE overlay；不解析导入表依赖链。  
- 不覆盖 Mach-O：只提取不解析。  

## 独立样本与可测点

| 语料 | 可测点 |
| --- | --- |
| `HMCL-3.15.2.exe` | MZ stub 自解压 PE、库数、导出表项、`ACC_NATIVE` 数、JNI 匹配应为 0 |
| `org.lwjgl.lwjgl:lwjgl:2.9.4-nightly-20150209` | 主 jar 的 `ACC_NATIVE` 数（2674）、独立工件里的库数（4）、单库导出数（2386）、JNI 按名匹配数（2383） |
| `org.lwjgl.lwjgl:lwjgl-platform:…:natives-windows` | 上述库的来源工件；`--libs-jar` 必须能从它读库 |

两个坐标都在 Maven Central，`--fetch-lwjgl DIR` 可直接下载，报告记录 sha256，  
因此这组证据是第三方可复现的。  

## 独立金标准

不取 `natives` / `analyze` 自身输出。`goldens.native_facts()` 直接读 PE 头  
（MZ → PE 签名 → COFF → 可选头 → 导出目录 RVA → 名称表）独立枚举导出名；  
`goldens.native_libs_facts()` 独立解析 natives 工件里的每个库；  
`goldens.jar_facts()` 独立统计 `ACC_NATIVE`。三条交叉验证：库数相等、单库  
导出数相等、`ACC_NATIVE` 数相等，且 `0 < jni_matched ≤ 独立统计的 Java_* 总数`。  

**这里修过一个真 bug**：RVA → 文件偏移的区间曾写成 `max(VirtualSize, 1 MiB)`，  
1 MiB 窗口互相覆盖，落在第三节的 RVA 被解析到第一节，于是 `lwjgl64.dll` 报出  
6218 个「导出」（真值 2386）、JNI 符号只认出 53 个（真值 2383）。现在区间用  
该节自己的 `VirtualSize`，只在它为 0 时退回 1 MiB 兜底；四个 DLL 的导出名与  
独立解析**逐名相等**。  

## 负控（构造方式与预期失败）

- `junit:junit:4.13.2`（纯 Java，公开可下载）：`libs=0`、`ACC_NATIVE=0`、  
  `jni_matched=0`，不得凭资源文件虚构库。  
- HMCL：有 69 个 `ACC_NATIVE` 但导出不是 JNI 符号，`jni_matched` 必须为 0——  
  证明「匹配数」不是只要有 native 就非零。  
- 单测：`--libs-jar` 指向一个只有假 `.dll` 的 jar 时，库被提取并标记来源工件，  
  但导出为 0；不存在的路径不产生库也不崩。  

## 与 03 阶段、独立研究线的边界

03 明确把 native 留在 Java 边界之外（`loadLibrary` 拒绝，不进入 Java 边界，  
`ROADMAP:218`），其隔离是 Java 级沙箱，不是 OS 边界。frida→Ghidra native  
深度还原、`RegisterNatives` 动态绑定还原属 `ROADMAP:231-236` 独立研究线，  
永不并入通用恢复承诺，本清单不把它们算 1.0 默认支持项。本笔记只做 PE / JNI  
层面的分诊、提取与按名匹配，不触碰函数体还原。
