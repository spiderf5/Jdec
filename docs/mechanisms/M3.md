# M3 invokedynamic / BootstrapMethods 站点与常量载荷还原

## 可观测形态（字节码 / 容器层面）

类文件的 `BootstrapMethods` 属性列出若干 bootstrap_method 条目（method_ref  
加参数），常量池里 `CONSTANT_InvokeDynamic` 通过 bootstrap_method_attr_index  
指向它们；每个 indy 调用点带 name_and_type。vanilla 编译产物的 bootstrap  
owner 集中在 `LambdaMetafactory` / `StringConcatFactory` / `ObjectMethods`；  
自定义 indy 混淆会出现非上述 owner 的 bootstrap、异常数量，或把常量 / 调用  
目标编码进 BSM 参数。特征是属性与常量池层面的，不含任何引导方法实现代码。  

三类 vanilla 工厂的静态参数含义不同，这也是可还原性的来源：

| owner | 静态参数 | 可还原的量 |
| --- | --- | --- |
| `LambdaMetafactory` | samMethodType、implMethod（MethodHandle）、instantiatedMethodType | 实现方法的 owner / 名称 / 描述符 |
| `StringConcatFactory` | recipe（`\u0001` 表示动态实参、`\u0002` 表示下一个常量）、常量列表 | 字符串拼接模板与其中的常量片段 |
| `ObjectMethods` | ClassDesc、组件名列表（分号分隔）、getter 句柄 | record 的组件名与类型 |

## 本工具的支持项

对真实 jar 执行 `indy --resolve`，枚举 `BootstrapMethods` 属性与全部 indy  
站点，按 bootstrap owner 与站点名归类，并还原每个站点携带的常量载荷：  

- `LambdaMetafactory` → 调用目标（owner / name / desc）；  
- `StringConcatFactory` → 格式模板与常量片段；  
- `ObjectMethods` → record 组件名与 getter 描述符。  

输入条件是 class 可解析、属性表完整、静态参数是常量（而非 ConstantDynamic）；  
产出是逐站点的载荷清单、三类还原计数与 owner 直方图。HMCL 实测  
**6245/6245 站点全部还原**（3899 lambda + 1667 concat + 679 record），  
NeoRaven **150/150**。  

支持项止于「还原 bootstrap 携带的常量」，**不执行 bootstrap**：调用点的  
运行时行为、非 vanilla 引导的调度语义都不在范围内。  

## 已知不覆盖

- 不执行 bootstrap、不实例化调用点；不还原非 vanilla 引导的调度语义。  
- 不还原把常量加密后交给自定义 BSM 解密的方案（ZKM 系 indy 字符串加密）：  
  这类站点的 recipe 不是明文字符串，本工具只枚举、不猜测。  
- `StringConcatFactory` 的 recipe 是 `CONSTANT_Dynamic` 时（罕见）不还原，  
  因为没有静态模板可读。  
- 不承诺把自定义 BSM 还原为等价 Java 源码。  
- **当前独立语料上非 vanilla 目标数为 0**：HMCL 的 6245 个、NeoRaven 的 150  
  个站点全部是三类 vanilla 工厂。因此「自定义 BSM 还原」这条路径**只有单元  
  级证据**，真实语料只证明了「如实报告 0」。

| 语料 | 可测点 |
| --- | --- |
| `HMCL-3.15.2.exe` | 站点总数、owner 直方图、三类载荷还原数、还原出的模板是否都存在于常量池、非 vanilla owner 计数（应为 0） |
| `NeoRaven1.1.jar` | 同类枚举在 PK jar 上的一致性（150/150）、非 vanilla owner 计数（应为 0）、无字符串加密载荷 |

## 独立金标准

不取 `indy` 自身输出。`src/jdec/goldens.py:bsm_facts()` 是**第二套解析器**  
（不 import 任何 jdec 分析模块），自己走一遍常量池与 `BootstrapMethods`：  
解析 `CONSTANT_MethodHandle → Methodref → Class → UTF8` 得到 owner 直方图，  
并收集全部静态 `CONSTANT_String` 参数。三条交叉验证：  

1. owner **集合**必须完全相等；  
2. 每个 owner 的站点数 ≥ 其独立条目数（一个条目可被多个站点共享）；  
3. 工具还原出的每个模板 / 组件列表必须**逐字存在**于独立收集的常量池载荷  
   集合中——伪造的字符串不可能出现在常量池里。  

实测 HMCL：1406 个去重载荷（1194 模板 + 212 组件列表）全部命中，0 例伪造。  
`javap -v` 仍可作为人工复核手段，但**未纳入自动回归**。  

## 负控（构造方式与预期失败）

负控语料 `junit:junit:4.13.2`（公开、未混淆、sha256 入库）：预期 `indy`  
报告 **0 个站点 / 0 个 BSM 条目**，不得出现 owner 或载荷计数；同时用于证明  
「report 6245」不是把任意 jar 都算上的恒真断言。  

另有一条单元级负控：`StringConcatFactory` 的模板必须落在常量池里，若把  
`resolve_concat` 的返回值改成一个常量池里没有的字符串，第 3 条交叉验证  
必须失败——这钉住「还原」不是「编造」。  

## 与 03 阶段、独立研究线的边界

03 把「indy 只有 fixture 级证据」明确留给 04（`ROADMAP:219`）。本笔记记录的  
是真实语料上的**载荷还原级**证据：vanilla 三类工厂的常量已全部取回，并有  
独立常量池交叉验证；但**没有执行 bootstrap，也没有行为对拍**，所以不是  
「语义等价」级证据。  

非 vanilla indy 混淆还原、BytecodeVM `$CodePool` 复现、把 VM 调度搬回字节码  
属 `ROADMAP:231-236` 独立研究线，永不并入通用恢复承诺，不算 1.0 默认支持项。  
两个语料都没有 `$CodePool`、没有非 vanilla BSM，目标数为 0，只如实报告，  
不记为已攻克。
