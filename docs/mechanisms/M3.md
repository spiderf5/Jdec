# M3 invokedynamic / BootstrapMethods 站点枚举

## 可观测形态（字节码 / 容器层面）

类文件的 `BootstrapMethods` 属性列出若干 bootstrap_method 条目（method_ref  
加参数），常量池里 `CONSTANT_InvokeDynamic` 通过 bootstrap_method_attr_index  
指向它们；每个 indy 调用点带 name_and_type。vanilla 编译产物的 bootstrap  
owner 集中在 `LambdaMetafactory` / `StringConcatFactory` / `ObjectMethods`；  
自定义 indy 混淆会出现非上述 owner 的 bootstrap、异常数量，或把常量 / 调用  
目标编码进 BSM 参数。特征是属性与常量池层面的，不含任何引导方法实现代码。  

## 本工具的支持项

对真实 jar 执行 `indy`，枚举 `BootstrapMethods` 属性与全部 indy 站点，按  
bootstrap owner 与站点名归类，产出站点清单（供字符串 / 调用目标编码线索）。  
输入条件是 class 可解析、属性表完整；产出是 owner × 站点名分组清单与总数。  
支持项止于「枚举与如实计数」，不执行 bootstrap、不解密自定义 recipe。  

## 已知不覆盖

- 不执行 bootstrap、不实例化调用点；不解密 recipe 之外的自定义引导逻辑。  
- 不还原把字符串 / 调用目标编码进 BSM 的混淆（indy 字符串加密、VM 级调度）。  
- 不承诺把自定义 BSM 还原为等价 Java 源码。  
- **当前独立语料上该机制的目标数为 0**：HMCL 的 6245 个、NeoRaven 的 150 个  
  indy 站点全部是 `LambdaMetafactory` / `StringConcatFactory` / `ObjectMethods`  
  等 vanilla 工厂，没有任何非 vanilla 自定义 BSM；支持项只是识别并**如实报告  
  0 个自定义目标**，不是「已攻克 indy 混淆」。  

## 独立样本与可测点

| 语料 | 可测点 |
| --- | --- |
| `HMCL-3.15.2.exe` | 站点总数、bootstrap owner 分组、非 vanilla owner 计数（应为 0）、BSM 参数里是否含编码常量 |
| `NeoRaven1.1.jar` | 同类枚举在 PK jar 上的一致性、非 vanilla owner 计数（应为 0） |

## 独立金标准

不取 `indy` 自身输出。用 `javap -v` 独立导出每个类的 `BootstrapMethods` 属性  
与 `CONSTANT_InvokeDynamic` / `CONSTANT_MethodHandle` 原始条目，按 owner FQCN  
逐条核对；用 `zipfile` 取 class 原始字节独立解析常量池。真值问题是「非  
vanilla owner 的站点是否真为 0、vanilla 站点计数是否与 javap 一致」，不是  
「indy 报了站点数」。  

## 负控（构造方式与预期失败）

构造 A：一个 class 的人工常量池里放一条 owner 为自定义类（非三种 vanilla  
工厂）的 `BootstrapMethods` 条目与一个 indy 站点，打成小 jar。预期工具必须  
把它计入「非 vanilla 自定义站点 ≥ 1」，**不得**仍报 0——用来证明「报告 0」  
不是恒真的空结论。构造 B：只有 vanilla lambda 的干净 jar。预期工具如实报告  
自定义目标 = 0，不得把 lambda 误标成混淆站点。两者夹逼「如实报告 0」的可信度。  

## 与 03 阶段、独立研究线的边界

03 把「indy 只有 fixture 级证据」明确留给 04（`ROADMAP:219`）；本笔记把它升级  
为真实语料上的**枚举级**证据，但**未解密、未重放、未行为对拍**，不是恢复级  
证据。非 vanilla indy 混淆还原、BytecodeVM `$CodePool` 复现、把 VM 调度搬回  
字节码属 `ROADMAP:231-236` 独立研究线，永不并入通用恢复承诺，不算 1.0 默认  
支持项。两个语料都没有 `$CodePool`、没有非 vanilla BSM，目标数为 0，只如实  
报告，不记为已攻克。
