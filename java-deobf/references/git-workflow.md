# Git 交付规范

仅在用户要求提交、建分支或出 PR 时使用。用户没提就不要自作主张提交 —— 改动留在工作区等他审阅。

## 动手前先看项目惯例

提交前先跑 `git log --oneline -20`，确认项目的既有风格：

- 提交信息的语言（中文还是英文）、有没有前缀（feat / fix / BRE-1234 之类的工单号）
- 是否有签名要求、是否有 commit lint、是否有 pre-commit 钩子
- **项目既有风格优先于本文件的默认约定。**

## 分支命名

| 类型 | 命名 |
|---|---|
| 新功能 | `feature/<简短描述>` |
| 修 bug | `fix/<简短描述>` |
| 重构 | `refactor/<简短描述>` |
| 依赖/配置/杂项 | `chore/<简短描述>` |

用英文小写加连字符。如果项目已有别的约定（比如带工单号 `feature/BRE-1234-xxx`），照项目的来。

## 提交信息

默认用 Conventional Commits，语言跟随项目既有风格：

```
<type>(<scope>): <一句话说明>

<body：为什么改，与改了什么；一段足够>

<footer：关联的 issue，或 BREAKING CHANGE 说明>
```

type 取值：`feat` / `fix` / `refactor` / `perf` / `test` / `docs` / `chore` / `build` / `ci`。

规则：

- 标题用祈使句，不超过 72 字符，结尾不加句号
- 标题写「做了什么」，正文写「为什么」；正文不要复述 diff
- 一个提交只做一件事 —— 修 bug 时顺手改的格式化，要么拆出来，要么别做
- 破坏性变更必须在 footer 写 `BREAKING CHANGE: ...`

## 粒度

- 按逻辑拆分：接口实现、测试、配置改动各自独立提交
- 不要把「实现 + 修自己刚引入的错 + 改格式」压成一个提交
- 修 bug 时：回归测试与修复可以是同一提交（测试是为了证明修复），也可拆成两个

## 提交前自检

1. `git diff` 逐个文件看一遍，确认没有夹带无关改动、调试代码、临时文件
2. 确认没有把密钥、`.env`、大文件、构建产物加进去
3. 确认校验命令全部通过（本仓库唯一命令：`python jdec/tests/run_tests.py`；
   改判定类逻辑时另做真实样本回归）
4. 在提交信息里写清改动原因与验证命令（不要追加过程性报告）
5. 只 `git add` 该提交的文件，不要用 `git add .` 一次全加

## PR / 交付描述

核心是让审阅者不用猜：

- 这次改了什么、为什么改
- 怎么验证（跑什么命令、看什么结果）
- 有没有风险、有没有没做完的事
- 影响面：是否改了接口契约、是否涉及数据迁移、是否需要灰度

**不要**把流水账原样贴进去 —— PR 描述面向审阅者，要的是判断依据。
