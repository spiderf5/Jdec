# 测试手册

## TDD 循环（红 → 绿 → 重构）

**适用**：新增有明确行为的业务逻辑、修 bug、重构前的保护网。
**不适用**：探索性原型、一次性脚本、纯配置改动 —— 这些写完再补测试即可。

```
红：先写一个会失败的测试，它精确描述期望行为
绿：用最小实现让它通过，不追求优雅
重构：消除重复、改善命名，测试全程保持通过
```

TDD 的价值不在仪式感，而在逼你**先想清楚「做对」长什么样**。
写不出失败的测试，说明需求还没想清楚 —— 这时该回去问，而不是先写代码。

### 循环纪律

- 一次只针对一个行为写一个测试，不要一次写十个再实现
- 红阶段必须亲眼看到它失败，并确认失败原因是「功能未实现」而不是「测试写错」
- 绿阶段允许丑陋实现；重构阶段再收拾
- 每完成一轮跑一次完整校验，不要攒着

## 为存量代码补测试（特征化测试）

给没有测试的旧代码补测试时，目标不是「测出它该是什么样」，而是**先固定它现在是什么样**：

1. **选目标**：优先选高风险、高改动频率、逻辑复杂的函数，而不是挑最容易的 getter。
2. **读既有测试**：照着项目已有测试的框架、命名、断言风格写，别自创一套。
3. **写特征化测试**：按当前实际行为写断言（哪怕行为看起来不合理），先建立保护网。
4. **确认是否合理**：如果当前行为明显是 bug，先向用户确认，再决定是改代码还是把 bug 固化下来。
5. **补边界**：见下方边界清单。
6. **评估缺口**：列出仍未覆盖的路径，写进报告，询问是否继续。

**关键**：不要边补测试边重构。先固定现状，再改行为，两件事分开做。

## 边界值清单

写用例时对照这张表，大多数 bug 都在里面：

| 类别 | 用例 |
|---|---|
| 空 | 空字符串、空数组、空对象、None/null |
| 单元素 | 只有一个元素的集合 |
| 边界数值 | 0、1、-1、最大值、最小值、刚好等于阈值 |
| 超长 | 超长字符串、超大数值、超大批次 |
| 非法输入 | 类型错误、格式错误、缺失必填字段 |
| 重复 | 重复提交、重复 ID、重复数据 |
| 并发 | 同一资源并发写、并发读-改-写 |
| 时序 | 超时、重试、乱序到达 |
| 权限 | 无权限用户、越权用户访问他人资源 |

## 测试替身的使用边界

**该替身**：外部服务（数据库、缓存、消息队列、第三方 API）、时间、随机数、文件系统。
**不该替身**：被测对象自身的内部方法（那样测的是 mock，不是代码）、简单的纯函数、值对象。

- 时间要可注入：用时钟接口或 fixture 固定时间，不要用 `sleep` 等异步完成
- 网络一律不打真实外部服务；集成测试单独分组，默认不跑
- 数据库优先用事务回滚或独立测试库，用例之间必须互相隔离

## 测试必须稳定

一个偶发失败的测试比没有测试更糟，它会消耗团队的信任。检查：

- 是否依赖用例执行顺序（共享状态、全局单例、静态变量）
- 是否依赖真实时钟、真实网络、真实文件系统路径
- 断言是否依赖浮点相等（应用近似比较）、集合顺序（应用集合比较）
- 并发测试是否有固定等待（应用条件等待而非固定 sleep）

## 覆盖率的正确用法

覆盖率用来**找缺口**，不是用来凑数字。

- 看的是「哪些分支没被覆盖」，不是「百分比到没到 80」
- 100% 覆盖率不代表测对了 —— 只调用不断言的测试覆盖率很高但毫无价值
- 危险信号：为凑覆盖率专门测 getter/setter、为私有方法写大量测试（应通过公开接口测）

## 断言写法

- 一个测试验证一个行为；多个断言可以，但必须围绕同一行为
- 断言要具体：断言「返回了什么」，而不是「没抛异常」
- 错误信息要能自解释：断言失败时，不看代码也知道哪错了
- 命名用 `given_条件_when_动作_then_结果` 或项目的既有风格，保持一致
