# 后端安全审查清单

**使用时机**：交付前自查的一部分，与 review-checklist.md 并行执行。
重点看**本次新增或改动的代码路径**，不必全量审计整个项目。
发现高危项必须修掉再交付；不能确定的，标为企业级风险写进报告，不要自行判定为安全。

## 注入类

| 检查 | 危险信号 |
|---|---|
| SQL 注入 | 字符串拼接进 SQL；ORM 的原生 SQL / `$queryRaw` / `createNativeQuery` 里拼用户输入 |
| 命令注入 | `exec` / `Runtime.exec` / `os.system` 的参数来自用户输入 |
| 模板注入 | 用户输入被当作模板渲染（SSTI） |
| NoSQL 注入 | MongoDB 查询条件直接由请求对象构造 |
| 路径穿越 | 文件路径拼接用户输入且未规范化；`../` 未过滤 |
| 日志注入 | 用户输入未转义直接写日志，可伪造日志行 |

**修法**：一律用参数化查询或预编译语句；不要用黑名单过滤替代参数化。

## 认证与授权

| 检查 | 危险信号 |
|---|---|
| 越权访问 | 只用当前用户 ID 查数据但没校验资源归属（水平越权）；接口没校验角色（垂直越权） |
| 鉴权缺失 | 新增接口没有鉴权注解/中间件；管理端接口与普通接口混在同一路由前缀 |
| 令牌处理 | JWT 未校验签名或过期；密钥硬编码；令牌写在 URL 里 |
| 默认策略 | 路由默认放行，靠逐个排除来限制（应为默认拒绝） |

**修法**：在 service 层校验资源归属，而不是只在网关或前端限制；新增接口明确标注所需权限。

## 输入校验

- 所有外部输入（含内部服务调用）都要校验类型、长度、范围、格式
- 文件上传：限制类型（看内容而非扩展名）、大小、存储路径；禁止用原始文件名直接落盘
- 批量接口要有数量上限，防止一次请求打满资源
- 反序列化：禁止反序列化不可信数据为任意类型

## 敏感信息

- 返回体：是否带出密码、令牌、身份证、手机号、内部 ID 等不该返回的字段
- 日志：是否打印了完整请求体、令牌、密码、密钥（应脱敏）
- 错误信息：是否把堆栈、SQL、内部路径返回给调用方（生产环境应统一错误响应）
- 代码：有无硬编码的密钥、AK/SK、数据库密码（应走配置或密钥管理）
- 配置文件：`.env` 是否进了版本库；`.env.example` 里是否只放占位值

## 依赖与配置

- 新增依赖是否有已知漏洞（先看项目的依赖审计命令）
- CORS 是否配置为允许任意来源且带凭证
- 安全响应头、HTTPS、Cookie 的 `HttpOnly`/`Secure`/`SameSite` 是否符合项目既有配置
- 调试接口、Swagger、管理后台在生产是否关闭或受限

## 资源与可用性

- 分页是否有最大页数或最大条数限制
- 递归/循环是否有明确终止条件；用户输入能否影响循环次数
- 大文件上传/下载是否有大小与超时限制
- 高频接口是否有限流；重试是否有退避与上限

## 加密与随机

- 密码是否用强哈希（bcrypt / argon2 / scrypt），禁止 MD5/SHA1 裸存
- 需要不可预测性的场景（令牌、验证码、订单号）是否用了安全的随机源，而非 `Math.random` / `rand`
- 敏感字段存储是否加密，密钥是否独立管理

## 交付前的最低要求

1. 注入类与越权类问题：**零容忍，必修**
2. 敏感信息泄漏：必修
3. 其余项：能修就修，修不了写进报告并标注风险等级
