# 交付前代码自查清单

**使用时机**：代码写完、校验命令全部跑通之后，交付之前。逐项过一遍，不要跳过。
这一步拦的是「能跑通但有隐患」的代码 —— 校验命令对此无能为力。

## 怎么过这份清单

对每个条目问一句「我的改动在这里有没有问题」，答不上来就去读代码确认。
发现的问题分三档处理，全部写进变更报告：

| 档位 | 含义 | 处理 |
|---|---|---|
| 必修 | 会导致错误行为、数据损坏或安全问题 | 立即改，改完重跑校验 |
| 建议 | 不影响正确性，但影响可维护性或性能 | 能改就改；改不动就在报告里说明原因 |
| 说明 | 已知取舍，本次有意不改 | 必须在报告里写清理由 |

## 1. 正确性

- 边界值：空集合、单元素、零、负数、极大值、超长字符串是否都处理了
- 空值与可选：可空字段是否都判空；Optional 是否被无条件解引用
- 异常路径：失败时的返回是否与正常路径结构一致；有没有静默吞掉异常
- 并发：共享状态是否被并发访问；读-改-写是否原子
- 幂等：重复提交同一请求会不会产生重复数据或重复副作用
- 事务边界：多步写操作是否在同一事务内；事务内是否有远程调用
- 时间：时区、精度、跨天/跨月边界；是否用了本地时间做业务判断

## 2. 错误处理

- 错误信息是否可定位（含关键上下文，但不泄漏内部细节）
- 是否把底层异常直接抛给调用方而没有包装
- 资源是否释放：连接、文件句柄、流、锁（放在 finally / defer / try-with-resources）
- 重试是否有限次与退避；重试的操作是否幂等

## 3. 数据一致性

- 数据库写入与缓存更新的顺序是否正确
- 删除缓存失败是否有补偿
- 并发更新同一行是否有乐观锁或唯一约束兜底
- 新增字段是否有默认值或迁移脚本；旧数据是否兼容

## 4. 性能

- 循环内是否有数据库查询或远程调用（N+1）
- 查询是否命中索引；新增的查询条件是否有对应索引
- 列表接口是否有分页或上限；会不会一次捞全表
- 是否有不必要的全量序列化/反序列化

## 5. 接口契约

- 请求/响应字段名、类型、单位是否与既有接口一致
- 是否破坏向后兼容（删字段、改类型、改语义）
- 错误码与 HTTP 状态码是否符合项目既有约定
- 新增必填字段是否会让老客户端调用失败

## 6. 可读性

- 命名是否表达了意图；有没有与既有代码冲突的同义词
- 函数是否过长或职责过多
- 是否有复制粘贴的重复逻辑（同一份逻辑出现两次就该抽出来）
- 注释是否解释「为什么」而不是复述代码；删掉复述型注释

## 7. 与项目一致

- 分层是否正确（controller / service / repository 是否放对了）
- 命名风格、日志方式、异常类型是否与同级代码一致
- 新依赖是否必要；项目里是否已有同类库
- 测试框架、断言风格、fixture 用法是否与既有测试一致

## 8. 测试

- 是否覆盖正常路径、边界值、错误路径三类
- 断言是否真的验证行为（只断言「不抛异常」等于没测）
- 测试是否稳定：不依赖执行顺序、不依赖真实网络与系统时钟
- 修 bug 的场景：新增的回归测试在修复前是否确实会失败

## 9. 遗留物

- 临时打印语句、调试代码、注释掉的代码块是否已清除
- TODO 是否写明责任人与后续动作
- 是否有无意中改动的无关文件（用 diff_summary.py 核对清单）
