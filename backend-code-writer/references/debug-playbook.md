# 后端排错手册

Mode B（修 bug）定位根因时查阅。核心原则：**修根因，不修表象；先复现，再动手。**

## 定位五步法

1. **确认失败点。** 拿到完整报错或失败测试，明确是哪一条命令、哪一个断言、哪一次请求失败。
   日志不足时先补观察手段，而不是先改代码。
2. **读栈顶，但不信栈顶。** 栈顶只是错误被抛出的位置。从栈顶开始，沿调用链往回找「状态第一次变错」的地方。
3. **追踪数据流。** 顺着输入 → 校验 → 业务处理 → 持久化 → 输出的路径检查每一步的值。
   在关键节点打印或断言中间值，比通读代码更快。
4. **二分缩小范围。** 用 `git bisect` 定位引入问题的提交；用最小输入集逐步去掉无关条件，找到触发的必要条件。
5. **固化成复现。** 把结论写成一个失败的单测或脚本。这一步做不出来，说明还没真正理解问题。

## 典型故障模式

| 症状 | 常见根因 | 检查方向 |
|---|---|---|
|  sporadic 500，重启后恢复 | 连接池耗尽、资源未释放、内存泄漏 | 连接/流的关闭是否在 `finally` 或 defer 中；池大小与并发量 |
| 偶发数据不一致 | 并发竞态、缺少事务或事务边界错误 | 读-改-写是否原子；事务注解是否生效（同类内部调用常导致失效） |
| 接口偶发超时 | N+1 查询、慢 SQL、同步阻塞调用 | ORM 是否预加载关联；有无索引；异步链路里是否混入阻塞 IO |
| 本地正常，线上失败 | 配置/环境差异、依赖版本漂移、时区 | 环境变量、配置文件差异；锁文件是否一致；时区与序列化格式 |
| 字段缺失或类型不对 | 序列化/反序列化不匹配、DTO 与实体混用 | 时间格式、数字精度、枚举映射、字段命名策略 |
| 重复提交产生脏数据 | 幂等缺失 | 唯一索引、幂等键、分布式锁 |
| 缓存与库不一致 | 更新顺序错误、过期策略不当 | 先更新库再删缓存；删除失败是否有补偿 |
| 测试单独跑通过，整体跑失败 | 测试间共享状态、顺序依赖、全局单例污染 | 数据库/缓存是否在用例间清理；有无共享的静态变量 |
| 升级依赖后报错 | 破坏性变更、传递依赖冲突 | changelog 中的 breaking change；锁文件 diff |

## 明确禁止的做法

- **猜测式修改**：没有证据就改代码，改完也不知道是否真的修好。
- **日志淹没**：到处加打印语句试图碰运气。定位阶段可以临时加，提交前必须清掉。
- **绕过失败**：删测试、放宽断言、加 `skip` / `@ts-ignore` / `# type: ignore` 让套件变绿。
- **附带重构**：修 bug 时顺手改命名、调格式、升依赖。这会让 diff 无法审阅，也会引入新风险。

## 修复完成的标准

- 原来的失败信号消失（有命令输出为证）。
- 完整校验套件通过，没有连带破坏（跑 `run_checks.py`）。
- 新增一条针对该 bug 的回归测试，且该测试在修复前会失败。
- 报告中写清「表象是什么、根因是什么、为什么这样改」。
